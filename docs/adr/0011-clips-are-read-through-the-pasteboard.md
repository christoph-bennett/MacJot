# Clips are read through ⌘C and the pasteboard

The Clip Hotkey presses ⌘C in the frontmost app, reads the pasteboard and restores the previous clipboard, which needs the Accessibility permission (macOS 27 lists it in System Settings as “Device Control and Data Access”) (decided 2026-11-15). We rejected reading the selection through the Accessibility API (the same permission, but text only, and it fails in browsers and Electron apps) and a Services menu entry (no permission, but its shortcut is assigned in System Settings, outside MacJot's Shortcuts pane); a Service ships beside it in the first version as a second path (revised 2026-11-15 after a sparring session: it is the sturdier path, with no permission, no clipboard trick and no timing, so it is not left for later), and Settings > Shortcuts says where its shortcut is set. The pasteboard route also hands MacJot whatever else the app copies, which later work on images needs. The capture sends only the Command flag after the hotkey's modifiers are released, reads once the pasteboard has settled, and never reads concealed items. The costs: clipboard managers see the ⌘C and the restore, and macOS ties the Accessibility grant to the app's code signature, so `scripts/bundle.sh` has to sign with a stable identity (the Apple Development certificate) instead of ad-hoc, or the grant resets at every install.
